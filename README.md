# totenkahn

Локальна платформа перевірки правил Sigma на збережених або зібраних Windows-подіях. Показує рішення правила, перевірки полів, блоки умови та докази. Підтримує керований запуск вибраних Atomic Red Team тестів.

## Готовий комплект і перший запуск

Розпакуйте комплект в окрему папку та відкрийте в ній PowerShell. Перед завантаженням модулів або виконанням Windows-перевірок у цьому самому вікні:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned -Force
```

Налаштування діє тільки в цьому процесі та його дочірніх процесах; після відкриття нового вікна команду треба повторити. Доменна Group Policy може мати пріоритет. Платформа не змінює Execution Policy або Defender автоматично.

Підготуйте базові залежності:

```powershell
.\totenkahn.exe dependencies prepare
.\totenkahn.exe dependencies status --json
.\totenkahn.exe doctor --mode replay --json
```

`prepare` показує план і запитує згоду. `--yes` означає явну неінтерактивну згоду. Перед встановленням виконується пошук наявних компонентів; сумісність визначається перевіркою проти зафіксованих пакетів. Зовнішні компоненти не перезаписуються й не стають власністю платформи.

На першому запуску встановлюються **лише powershell-yaml та Invoke-AtomicRedTeam**. Бібліотеки застосунку включено до комплекту. Загальний каталог Atomic, виконувані ресурси та передумови всіх тестів не встановлюються. Звичайні Windows-запуски також пропонують базову підготовку, якщо вона потрібна; `--help`, CI та явно вибраний replay без залежностей її не запускають.

Якщо є підготовлений кеш, доступний офлайн-режим:

```powershell
.\totenkahn.exe dependencies prepare --offline --cache .\.totenkahn-package-cache
```

Кеш містить `<sha256>.package` відповідно до `config/dependencies.lock.json`. Відсутність пакета в офлайн-режимі є поясненою неготовністю, а не успіхом встановлення.

## Replay без Atomic

Приклад використовує тільки синтетичні збережені події з комплекту:

```powershell
.\totenkahn.exe --session .\examples\regression\session --rule .\examples\ci\candidate.yaml --test-case .\examples\regression\positive.json --skip-dependencies
```

`--skip-dependencies` дозволений лише для replay/regression. Він не дозволяє обійти готовність live-режимів. HTML/JSON-звіти пояснюють вибрані події, наявність полів, результати модифікаторів, блоків та підсумкової умови. Недостатність доказів відрізняється від негативного результату правила.

```powershell
.\totenkahn.exe reports
.\totenkahn.exe reports --open
```

`reports --open` відкриває наявний каталог звітів у Windows. Звичайний replay не є CI-критерієм проходження: для контрольованих exit codes використовуйте `ci`.

## Вибраний Atomic-тест

Спочатку мають бути готові базові модулі. Приклад нижче **лише планує та готує ресурси**, не запускає тест:

```powershell
.\totenkahn.exe dependencies plan-test --technique T1059.003 --test-number 2
.\totenkahn.exe dependencies prepare-test --technique T1059.003 --test-number 2
```

План може завантажити зафіксований архів Atomic у кеш, але не розпаковує всі техніки. Підготовка матеріалізує YAML вибраної техніки та визначені ресурси конкретного тесту. YAML техніки може містити описи інших тестів; це не дозвіл на їх виконання. Динамічні посилання, які неможливо визначити статично, потребують розгляду та явних `--asset-file` або `--asset-technique`. Значення `--input NAME=VALUE` мають відповідати майбутньому плану запуску.

Заблокований або відсутній ресурс фіксується з причиною; незалежні ресурси можуть бути підготовлені. Вибраний тест залишається неготовим, але базові модулі й replay не стають недоступними. Сам `prepare-test` повертає неуспішний статус, якщо підготовка неповна. Код помилки без підтвердження не оголошується блокуванням Defender.

Перегляд плану після підготовки:

```powershell
.\totenkahn.exe --auto --atomic-test T1059.003 2 --atomic-plan
```

Для реального запуску потрібне власне сумісне правило, готова телеметрія та явне підтвердження плану. CLI:

```text
totenkahn.exe --rule RULE.yaml --auto --atomic-test TECHNIQUE NUMBER --cleanup
```

`RULE.yaml`, `TECHNIQUE`, `NUMBER` — параметри інженера, не готовий приклад для копіювання. Підтримуються Windows executors `powershell` і `command_prompt`. `--approve-atomic` підтверджує виконання без діалогу. `--prepare-prereqs` окремо дозволяє команди передумов **вибраного** тесту. `--cleanup` виконує cleanup із його визначення; це не гарантія повного відновлення хоста. Підготовка файлів, виконання передумов, виконання Atomic та результат детекції мають окремі стани.

## Live-телеметрія

Для власного правила доступні:

```text
totenkahn.exe telemetry plan --rule RULE.yaml
totenkahn.exe telemetry prepare --rule RULE.yaml
totenkahn.exe telemetry check --rule RULE.yaml
totenkahn.exe --manual --rule RULE.yaml
```

`plan` і `check` перевіряють стан. `prepare` показує зміни та запитує згоду; для змін потрібні права адміністратора. Для Security підтримано Process Creation / 4688 та запис командного рядка. Для Sysmon — документовані в коді категорії process_creation, network_connection, image_load, file_event, registry_event, dns_query. Непідтримані вимоги не оголошуються готовими.

Встановлення відсутнього standalone Sysmon є окремою дією з перевіркою Microsoft Authenticode та явним `--accept-sysmon-eula`. Наявні зовнішні конфігурації та конфлікт із native Sysmon не перезаписуються автоматично. Системні налаштування можуть впливати на весь хост; готовність конфігурації ще не доводить надходження подій.

Відновлення підтверджених власних змін:

```powershell
.\totenkahn.exe telemetry restore --dry-run
.\totenkahn.exe telemetry restore
```

Змінені сторонніми процесами значення, непідтверджені операції та чужі журнали не відновлюються навмання. Журнал змін не видаляйте до відновлення. Live/Atomic-приймання актуальної збірки ще потрібне.

## Видалення

```powershell
.\totenkahn.exe dependencies remove --dry-run
.\totenkahn.exe dependencies remove
```

Друга команда запитує підтвердження. Для автоматизації є `--yes --json`. Видаляються тільки підтверджені власні незмінені залежності; сторонні компоненти, змінені файли, звіти, сесії, кеш і журнали зберігаються. Ця команда не видаляє portable-комплект і не відновлює налаштування телеметрії.

Для повного виведення з експлуатації спочатку відновіть власні зміни телеметрії, потім видаліть залежності, закрийте процес і приберіть папку розпакованого комплекту. Автоматичного безумовного видалення всіх даних однією командою немає; попередня вимога повного lifecycle ще потребує фінального приймання.

## Старий managed setup

`totenkahn-setup.exe` з командами `install`, `uninstall`, `doctor` збережено для окремого managed-сценарію та його тестів. Це реалізований старий інтерфейс, **не основний portable/first-run workflow** і не підтвердження завершеності всього встановлення. Він копіює перевірений реліз, готує два базові модулі та веде власний журнал; вибрані Atomic-ресурси й телеметрія залишаються окремими.

Історичні Windows-результати DVP не сертифікують перейменовану збірку. Тому універсальну рекомендацію `setup.exe install` прибрано з основного старту. Повний перелік опцій старого інтерфейсу доступний через `totenkahn-setup.exe --help`; для його видалення потрібна зовнішня копія setup та точний каталог встановлення.

## Detection CI

```powershell
.\totenkahn.exe ci --config .\examples\ci\pipeline.json --output-dir .\ci-results
```

Каталог результатів має бути новим. Шляхи jobs відраховуються від JSON-конфігурації. Схема: `schema_version: 1`, `gates`, непорожній `jobs`; кожен job містить `id`, `suite`, `baseline`, `candidate`.

Типові пороги на job: `max_regressed: 0`, `max_not_met: 0`, `max_insufficient: 0`, `min_cases: 1`. Є JSON/HTML-підсумок, докладні звіти з доказами та JUnit. Недостатність даних не вважається успіхом. JUnit зберігає сирі невідповідності навіть за послаблених порогів, тому зовнішній JUnit publisher може бути суворішим за exit code.

| CI exit code | Значення |
| --- | --- |
| 0 | Налаштовані критерії виконані |
| 1 | Порушення критеріїв |
| 2 | Помилка входів, виконання або запису |
| 130 | Переривання |

Це контракт `ci`, а не всіх команд. Для керування залежностями/телеметрією статус JSON є первинним поясненням; зазвичай 1 означає блокування, 2 — помилку, 3 — потребу перевірки. Неготовність необов'язкових компонентів може дати `passed_with_warnings` у прийманні кандидата, але не перетворює неповне встановлення компонента на успіх.

Workflows `.github/workflows/ci.yml` і `windows-candidate.yml` реалізують перевірки push/PR та ручну Windows-збірку відповідно. Вони зберігають діагностику й кандидат як artifact; не публікують фінальний GitHub Release та не запускають Atomic. Для використання файли мають бути у GitHub-репозиторії. Фактичний запуск workflow ще потрібно підтвердити.

## Збірка та перевірки для розробника

Python 3.12+; рекомендована CI-конфігурація використовує 3.13. На Windows із кореня source checkout:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned -Force
py -3 -u -B scripts/build_windows_acceptance.py --source-commit YOUR_40_CHARACTER_COMMIT
```

Замініть `YOUR_40_CHARACTER_COMMIT` на реальний базовий commit. Builder створює окреме середовище, встановлює зафіксовані прямі залежності, перевіряє типи й source-тести, збирає обидва exe, перевіряє frozen CI, формує маніфест та запускає acceptance. Виводить точний build directory і `build-report.json`.

Старий `prepare_acceptance_release.py` із фіксованим каталогом історичної збірки вимкнено; використовуйте builder вище.

Для окремої перевірки у вже підготовленому Python-середовищі:

```powershell
python -B scripts/check_quality.py
python -u -B scripts/check_setup_stage.py --source-only
python -B main.py ci --config examples/ci/pipeline.json --output-dir ci-results
```

Source-тести інертні, але деякі завантажують тестові PowerShell-модулі, тому сумісна Execution Policy потрібна навіть без Atomic-виконання. Пропущений платформний тест не вважається повним прийманням.

Після успішної Windows-збірки:

```text
python -B scripts/package_ci_release.py --build-dir BUILD_DIRECTORY --output-dir delivery
```

Експорт містить повний `totenkahn-windows-candidate.zip`, SHA256SUMS і звіти. Змінений маніфест, провал core/CI або суперечливі статуси блокують експорт. Необов'язкові залежності можуть бути недоступні в hosted runner без кешу — це явно записане обмеження. Кандидат не є підписаним фінальним релізом. Версії та hashes записуються, але runner images, major tags Actions і транзитивні пакети не забезпечують побайтово відтворюваної збірки.

## Межі поточної версії

- Підтримується реалізована підмножина Sigma; непідтримані модифікатори й умови відхиляються.
- Позитивний результат правила, достатність вибраних доказів, успішність Atomic та готовність телеметрії — різні твердження.
- Реалізація CI/CD завершена локально; її hosted-виконання та актуальне Windows/live-приймання залишаються перевірками перед релізом.
- До погодженого MVP залишається один великий етап: фінальне Windows/live-приймання та готовий реліз. Перейменування потребує нової збірки, старі exe автоматично не змінюються.
