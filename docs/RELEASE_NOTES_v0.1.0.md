# Totenkahn v0.1.0

Дата підготовки: 2026-11-28. Версію погоджено. Це опис релізу для фінальної збірки та review; сам файл не свідчить про публікацію GitHub Release.

## Призначення

Локальна платформа для аналізу доказів, Threat Hunting і перевірки детекцій. Пояснює рішення правила та зберігає зв'язок між оригінальною подією, перетворенням полів, умовою, знахідкою й результатом регресійної перевірки.

## Склад v0.1.0

- Імпорт дампів, збереження оригіналів і контрольних сум, профілі нормалізації, оцінка якості та відновлення зі збережених доказів. Формати й обмеження наведено в README.
- Sigma-аналіз із поясненнями та розрізненням MATCH, NO MATCH і INSUFFICIENT DATA. Підтримка обмежена реалізованими умовами/модифікаторами; не заявляється повна сумісність із довільним Sigma-правилом.
- Case, timeline, окремі нотатки аналітика, експорт доказів, Hunting, переглянуті findings і регресійні перевірки.
- Ручні й автоматичні Windows-сценарії, облік залежностей і вибіркова підготовка Atomic-ресурсів. Передумови й виконання конкретного тесту потребують окремого погодження.
- Source CI, порівняння незмінних Git-ревізій правил, ручне живе приймання через Elastic, перевірена доставка, явна активація та rollback попереднього прийнятого пакета.
- Компактний англомовний банер: назва та v0.1.0. README містить повний порядок CI/CD у форматі решти команд.

## Відомі обмеження

- Живий контракт Elastic перевірено на двох процесних подіях. Він не підтверджує появу EDR-алертів, повноту телеметрії хоста, автоматичне реагування або універсальну сумісність XDR.
- Реальне приймання Splunk у цьому циклі не надано. Наявність профілів імпорту не означає підтвердження всіх виробників, версій і форматів експорту.
- API-запити до Elastic виконує workflow. Платформа імпортує отримані fields-документи; постійний універсальний SIEM-конектор не заявляється.
- GitHub offline acceptance B містила попередження: у кеші не було powershell_yaml та Invoke-AtomicRedTeam. Це не блокує перевірені офлайн-можливості, але не є підтвердженням Atomic readiness на сервері. У цьому живому циклі Atomic не виконувався.
- Локальні хеші й журнали забезпечують перевірку узгодженості, але не цифровий підпис видавця й не незалежно засвідчений chain of custody.
- Rollback перемикає програму; він не скасовує зміни хоста, передумови Atomic або міграції формату даних. Старі слоти й докази автоматично не видаляються.
- Немає автоматичної доставки правил у Splunk/Elastic або автоматичної публікації релізу.

## Пакет публікації та завершення

Публікуйте лише пакет із фінального прийнятого коміту. Збережіть повний Windows ZIP, `SHA256SUMS`, `RELEASE_SHA256SUMS`, `delivery-review.json`, build/acceptance/CI-звіти та цей опис. Повні лабораторні події й локальні шляхи не потрібно завантажувати в публічний репозиторій; зберігайте їх окремо від загальнодоступних матеріалів.

Перед публікацією:

1. Закомітити зміни v0.1.0 й прийняти source CI.
2. Зібрати фінальний Windows candidate саме з цього коміту. Перевірити версію `0.1.0` у release manifest та `v0.1.0` у банері.
3. Виконати stage/test нового пакета на сервері, переглянути warnings і активувати його за явною згодою. Зберегти новий release ID і receipt.
4. Прив'язати тег `v0.1.0` до цього коміту, підготувати GitHub Release з відповідними артефактами й лише після review опублікувати.

Тег, commit і публікація не створюються автоматично зміною README або значення VERSION. Статус підготовки не слід підміняти статусом фінального приймання нової збірки.
